# Release notes: 2026-09-30

First production deployment setup: hosting the app at **https://flights.wyattmunson.com** on a
single AWS Lightsail VM running k3s, with a shared CloudNativePG Postgres. No application code
(API, web, shared package) changed; everything added is deployment tooling.

Status at time of writing: AWS resources exist, k3s is installed, SSH and the kubectl tunnel work,
and the CloudNativePG operator and secrets are in place. The Traefik TLS config needed a fix (see
[Pitfalls](#pitfalls)). The platform Postgres cluster and the app itself were not yet confirmed
running. Backups are not configured. Nothing in the manifests had been run on a real cluster before
this work, so treat the setup docs as first-pass and expect to correct them.

## What was added

| Path                               | What                                                                                                                                      |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `deploy/docker/`                   | Production `api` and `web` Dockerfiles, API entrypoint (migrate → seed → serve), nginx config                                             |
| `deploy/k8s/platform/`             | Pinned CloudNativePG operator (v1.30.1), shared `platform-pg` Postgres cluster, per-app role and `Database`, Traefik Let's Encrypt config |
| `deploy/k8s/apps/flight-log/`      | Namespace, api + web Deployments and Services, Traefik middlewares (basic auth, HTTPS redirect) and routes for `flights.wyattmunson.com`  |
| `deploy/bootstrap/install-k3s.sh`  | Scripted version of the node setup (disk mount, unattended upgrades, k3s install)                                                         |
| `deploy/scripts/create-secrets.sh` | Scripted version of the secret creation                                                                                                   |
| `deploy/aws/`                      | `provision.sh` (Lightsail instance, static IP, data disk, firewall, snapshots, Route 53 record), `iam-policy.json`, and `README.md`       |
| `deploy/README.md`                 | Runbook for the whole deploy                                                                                                              |
| `.github/workflows/images.yml`     | Builds and pushes `ghcr.io/wyattmunson/flight-log-{api,web}` on every push to `main`                                                      |

Design choices worth knowing:

- **Shared database.** One CloudNativePG cluster (`platform-pg`, namespace `databases`, 1 instance,
  10 Gi) hosts a database and role per app, so more apps can be added to the node later. The app
  connects to `platform-pg-rw.databases.svc.cluster.local`.
- **Auth is HTTP basic auth at Traefik.** The app has no login of its own (every request acts as the
  seeded user), so the whole host, API included, is behind a Traefik `basicAuth` middleware.
- **TLS** is Let's Encrypt HTTP-01 through the k3s-bundled Traefik. DNS must be DNS-only (not proxied).
- **API is 1 replica with the `Recreate` strategy** because import previews live in process memory.
  A deploy drops any pending import preview.
- **Swagger UI is off** (`ENABLE_API_DOCS=false`) on the public host.
- **Container hardening.** Both images run non-root with a read-only root filesystem and all
  capabilities dropped; `/tmp` is an `emptyDir`.
- **First API boot** downloads about 12k airports and 6k airlines (OurAirports, OpenFlights), so the
  pod needs outbound internet and the startup probe allows up to 5 minutes.
- **Web image build** copies `tsconfig.base.json` into the build stage; Vite's build fails without it.

## AWS resources

Region `us-east-1`, zone `us-east-1a`. About $27/mo.

| Resource                        | Details                                                          |
| ------------------------------- | ---------------------------------------------------------------- |
| Lightsail instance `flight-log` | Ubuntu 24.04, 4 GB RAM / 2 vCPU / 80 GB SSD (`medium_3_0`), IPv4 |
| Static IP `flight-log-ip`       | Attached to the instance                                         |
| Data disk `flight-log-data`     | 20 GB, holds k3s volumes (Postgres, Traefik cert store)          |
| Key pair `flight-log-kp`        | Lightsail key pair; private key at `~/.ssh/flight-log-kp.pem`    |
| Firewall                        | 22 from one IP only, 80 and 443 from anywhere; 6443 stays closed |
| Disk auto-snapshots             | Daily, 7 retained                                                |
| Route 53                        | `A flights.wyattmunson.com` → static IP, TTL 300, DNS-only       |

### Commands

Create the Lightsail key pair (the private key is shown once, so save the file):

```bash
aws lightsail create-key-pair --region us-east-1 --key-pair-name flight-log-kp \
  --query privateKeyBase64 --output text > ~/.ssh/flight-log-kp.pem
```

```bash
chmod 600 ~/.ssh/flight-log-kp.pem
```

Provision the instance, static IP, disk, firewall, snapshots and DNS record. The script prints a plan
with prices and waits for `y`. It is safe to re-run; existing resources are reused:

```bash
KEY_PAIR=flight-log-kp deploy/aws/provision.sh
```

If the script stops partway (see the disk-attach pitfall below), finish the remaining steps in the
Lightsail console:

1. **Attach the disk.** Storage → `flight-log-data` → Attach to instance → `flight-log`. Do not
   format or mount it in the console.
2. **Firewall.** Instance → Networking → IPv4 Firewall: SSH 22 restricted to your IP, HTTP 80 any,
   HTTPS 443 any.
3. **Snapshots.** Storage → `flight-log-data` → Snapshots → enable automatic snapshots.
4. **DNS.** Route 53 → hosted zone `wyattmunson.com` → create an `A` record `flights` with the
   static IP, TTL 300, simple routing, alias off. Get the IP with:

```bash
aws lightsail get-static-ip --static-ip-name flight-log-ip --query staticIp.ipAddress --output text
```

Verify:

```bash
dig +short flights.wyattmunson.com
```

## Node setup (on the VM)

Connect with:

```bash
ssh -o IdentitiesOnly=yes -i ~/.ssh/flight-log-kp.pem ubuntu@<static-ip>
```

Confirm the data disk (expect `nvme1n1`), and that it has no filesystem before formatting:

```bash
lsblk
```

```bash
sudo blkid /dev/nvme1n1
```

Format it and mount it where k3s stores volumes:

```bash
sudo mkfs.ext4 -L k3s-storage /dev/nvme1n1
```

```bash
sudo mkdir -p /var/lib/rancher/k3s/storage
```

```bash
echo "UUID=$(sudo blkid -s UUID -o value /dev/nvme1n1) /var/lib/rancher/k3s/storage ext4 defaults,nofail 0 2" | sudo tee -a /etc/fstab
```

```bash
sudo mount -a && df -h /var/lib/rancher/k3s/storage
```

Patch the OS and make sure automatic security updates are on:

```bash
sudo apt-get update && sudo apt-get -y upgrade
```

```bash
sudo apt-get install -y unattended-upgrades
```

Install k3s. The config keeps the API server on localhost and encrypts secrets at rest:

```bash
sudo mkdir -p /etc/rancher/k3s
```

```bash
printf 'write-kubeconfig-mode: "0600"\nsecrets-encryption: true\n' | sudo tee /etc/rancher/k3s/config.yaml
```

```bash
curl -sfL https://get.k3s.io | sudo INSTALL_K3S_CHANNEL=stable sh -
```

Verify: the node should be `Ready`, and `traefik`, `coredns`, `local-path-provisioner` and
`metrics-server` should reach `Running`:

```bash
sudo k3s kubectl get nodes
```

```bash
sudo k3s kubectl get pods -A
```

## Cluster access from the laptop

The Kubernetes API is not exposed publicly. Copy the kubeconfig (its server is already
`https://127.0.0.1:6443`) and reach it through an SSH tunnel:

```bash
mkdir -p ~/.kube && ssh -o IdentitiesOnly=yes -i ~/.ssh/flight-log-kp.pem ubuntu@<static-ip> 'sudo cat /etc/rancher/k3s/k3s.yaml' > ~/.kube/flight-log.yaml && chmod 600 ~/.kube/flight-log.yaml
```

Keep this running in its own terminal tab whenever you use `kubectl`:

```bash
ssh -o IdentitiesOnly=yes -i ~/.ssh/flight-log-kp.pem -N -L 6443:127.0.0.1:6443 ubuntu@<static-ip>
```

In every shell that runs `kubectl` for this cluster:

```bash
export KUBECONFIG=~/.kube/flight-log.yaml
```

```bash
kubectl get nodes
```

## Deploying the platform and app

Images must exist first. Set your Let's Encrypt email in `deploy/k8s/platform/traefik-config.yaml`
(replace `you@example.com`), push to `main` so the `images` workflow runs, then set both GHCR
packages (`flight-log-api`, `flight-log-web`) to **Public** in GitHub package settings.

Install the database operator:

```bash
kubectl apply --server-side -k deploy/k8s/platform/cnpg-operator
```

```bash
kubectl -n cnpg-system rollout status deploy/cnpg-controller-manager
```

Namespaces and secrets:

```bash
kubectl create namespace databases
```

```bash
kubectl create namespace flight-log
```

```bash
DB_PASS=$(openssl rand -hex 24)
```

```bash
kubectl -n databases create secret generic flight-log-db-credentials --type=kubernetes.io/basic-auth --from-literal=username=flight_log --from-literal=password="$DB_PASS"
```

```bash
kubectl -n databases label secret flight-log-db-credentials cnpg.io/reload=true
```

```bash
kubectl -n flight-log create secret generic flight-log-db --from-literal=DATABASE_URL="postgresql://flight_log:${DB_PASS}@platform-pg-rw.databases.svc.cluster.local:5432/flightlog"
```

The site login. The username is `wyatt`; the password is whatever you enter at the prompt:

```bash
read -r -s -p "Site password: " SITE_PW; echo
```

```bash
kubectl -n flight-log create secret generic flight-log-basic-auth --from-literal=users="wyatt:$(printf '%s' "$SITE_PW" | openssl passwd -apr1 -stdin)"
```

```bash

```

Apply the platform (Postgres cluster and Traefik config), then the app:






The first API start runs migrations and downloads reference data, so allow a few minutes
(`kubectl -n flight-log logs deploy/api -f`). Then browse to https://flights.wyattmunson.com and

## Pitfalls

### Lightsail `ImportKeyPair` rejects a valid local public key

Symptom: `InvalidInputException ... The format of this public key is not valid`, even though the
`.pub` file is valid.

Correct approach: create the key pair in Lightsail and use it.

```bash
aws lightsail create-key-pair --region us-east-1 --key-pair-name flight-log-kp \
  --query privateKeyBase64 --output text > ~/.ssh/flight-log-kp.pem
```

Notes:

- Lightsail key pairs are separate from EC2 key pairs and are per region. An EC2 key pair of the
  same name is not usable. List Lightsail ones with `aws lightsail get-key-pairs --region us-east-1`.
- The private key is returned once and cannot be recovered. Back it up.
- `provision.sh` now takes an existing Lightsail key pair through `KEY_PAIR` and fails early if it
  isn't found.

### `AttachDisk` fails with "Not authorized to call API with parameter autoMounting"

Symptom: the provisioning script creates the instance, static IP and disk, then stops at attaching
the disk.

Correct approach: attach without any auto-mounting parameter (the script no longer passes one), or
attach in the console (Storage → disk → Attach to instance). The disk is formatted and mounted
manually on the VM afterwards. Re-running `provision.sh` after the fix is safe, because existing
resources are reused. The remaining steps (firewall, snapshots, DNS) can also be done in the console.

### SSH: `Permission denied (publickey)`

Correct command:

```bash
ssh -o IdentitiesOnly=yes -i ~/.ssh/flight-log-kp.pem ubuntu@<static-ip>
```

Notes:

- The user is `ubuntu`.
- `IdentitiesOnly=yes` stops the client offering other keys (from an agent or default paths) before
  the right one.
- If you use a `~/.ssh/config` `Host` entry, its `IdentityFile` must be `~/.ssh/flight-log-kp.pem`.
  A stale entry pointing at a different key file gives this error even though the direct command
  works.
- To confirm the instance's key pair:
  `aws lightsail get-instance --region us-east-1 --instance-name flight-log --query 'instance.sshKeyName'`

### `kubectl` fails with `dial tcp 127.0.0.1:<random port>: connection refused`

Cause: `kubectl` is using a different kubeconfig or context (a local cluster such as Docker Desktop,
minikube or kind) because `KUBECONFIG` was set in another terminal, or the SSH tunnel isn't running.
A port other than `6443` in the error is the sign.

Correct approach:

```bash
export KUBECONFIG=~/.kube/flight-log.yaml
```

```bash
kubectl get nodes
```

The tunnel must be running for this to work. If `connection refused` is on port `6443`, restart the
tunnel. Also check that earlier commands (operator install, namespace creation) did not land on the
other cluster:

```bash
kubectl config get-contexts
```

If they did, remove them from that context with
`kubectl --context <context> delete namespace databases flight-log cnpg-system`. Also make sure
`DB_PASS` is still set in the shell before creating secrets (`[ -n "$DB_PASS" ] && echo set`), or the
secret is created with an empty password. Using `--kubeconfig ~/.kube/flight-log.yaml` on each command,
or exporting it in the shell profile, avoids this.

### Traefik rollout stuck: one pod `Running`, one `Init:Error`

Cause: the `volume-permissions` init container in `deploy/k8s/platform/traefik-config.yaml` ran
`chown` as the non-root Traefik user (UID 65532), which is not permitted. The old pod keeps serving
while the new one restarts.

Diagnose:

```bash
kubectl -n kube-system get pods -l app.kubernetes.io/name=traefik
```

```bash
kubectl -n kube-system logs <init-error-pod> -c volume-permissions
```

Correct config: the init container only needs to create the certificate store with mode 0600:

```
touch /data/acme.json && chmod 600 /data/acme.json
```

The `chown` has been removed in the repo. Re-apply so the cluster re-renders Traefik:

```bash
kubectl apply -k deploy/k8s/platform
```

```bash
kubectl -n kube-system get pods -l app.kubernetes.io/name=traefik -w
```

```bash
kubectl -n kube-system exec deploy/traefik -- ls -l /data
```

Expect a single `Running` pod and `acme.json` with `-rw-------`. The init command runs
automatically on every Traefik start; it is not something to run by hand.

Related: while debugging certificate issuance, uncomment the staging `caserver` line in
`traefik-config.yaml` to avoid Let's Encrypt rate limits. Remove it afterwards, delete
`/data/acme.json` in the Traefik pod, and restart Traefik to get a trusted certificate.

### Forgotten basic-auth password

Only a hash is stored, so it can't be read back. Confirm the username:

```bash
kubectl -n flight-log get secret flight-log-basic-auth -o jsonpath='{.data.users}' | base64 -d | cut -d: -f1
```

Reset the password (Traefik picks it up without a restart):

```bash
read -r -s -p "New site password: " SITE_PW; echo
```

```bash
kubectl -n flight-log create secret generic flight-log-basic-auth --from-literal=users="wyatt:$(printf '%s' "$SITE_PW" | openssl passwd -apr1 -stdin)" --dry-run=client -o yaml | kubectl apply -f -
```

```bash
unset SITE_PW
```

### Pods in `ImagePullBackOff`

GHCR packages are private the first time they are pushed. Set `flight-log-api` and `flight-log-web`
to **Public** in GitHub → Packages → Package settings → Change visibility. The images contain no
secrets or data.

## Known gaps

- **No backups.** Data is protected only by daily disk snapshots, which are crash-consistent. Add a
  CloudNativePG `backup.barmanObjectStore` and `ScheduledBackup` in
  `deploy/k8s/platform/postgres/cluster.yaml` before storing data that can't be re-imported.
- **Single node, single Postgres instance.** A reboot means brief downtime.
- **SSH is restricted to one IP.** Re-run `deploy/aws/provision.sh` (or edit the firewall rule) when
  your IP changes.
- **Billing.** Lightsail bills stopped instances; delete rather than stop. Teardown commands are in
  `deploy/aws/README.md`.
