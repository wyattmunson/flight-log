# Release notes: 2026-09-30 (in-app authentication)

Email + password login with database-backed sessions, replacing the Traefik HTTP basic auth in front
of https://flights.wyattmunson.com. This is a second note for the same day; the deployment setup
itself is in [`2026-09-30.md`](2026-09-30.md).

Status at time of writing: implemented and tested locally (unit, integration and browser checks).
**Nothing has been applied to the cluster and no images have been pushed.** The rollout below is
unrun, and two parts of it could not be tried locally (see [Known gaps](#known-gaps)).

Auth is opt-in: with `AUTH_REQUIRED` unset (local dev, `docker compose up`) the app behaves exactly as
before, with every request acting as the seeded default user and no login UI. The production
manifests now set `AUTH_REQUIRED=true`.

## What changed

| Area      | Change                                                                                                                                                                                             |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Database  | `users.password_hash` (nullable) and a `sessions` table (token stored as SHA-256 hex, `ON DELETE CASCADE`). Migration `add_auth`; run automatically on API start.                                  |
| API       | `src/auth/` (scrypt hashing, cookies, throttle, sessions, user admin), `dal/auth.ts`, `routes/auth.ts`, `http/csrf.ts`. `resolveUser` is still the only place `req.userId` is set.                 |
| Endpoints | `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, `POST /api/auth/password`. Documented in Swagger (`/api/docs`) with the 401/403/429 responses and the cookie security scheme. |
| CLI       | `npm run user:create` (also `--adopt-default`) and `npm run user:set-password` in `apps/api`.                                                                                                      |
| Web       | `/login`, `/account/password`, a route guard, a user menu (hidden when auth is off), and a global 401 handler that returns to `/login` with the page you were on.                                  |
| Deploy    | `AUTH_REQUIRED=true` in the API ConfigMap; the basic-auth Middleware and its route references removed; `create-secrets.sh` no longer takes a username or creates the basic-auth secret.            |

Behavior worth knowing:

- **Passwords:** scrypt (N=2^15, r=8, p=1), 12 to 128 characters, no composition rules, not equal to
  the email. The parameters are stored in each hash, so they can be raised later.
- **Sessions:** 30-day sliding expiry, refreshed at most hourly (the cookie is re-sent when it is).
  Cookie `flightlog_session`: HttpOnly, SameSite=Lax, Secure in production.
- **Login throttle:** in memory, per API process. 10 attempts per email and 30 per IP per 15 minutes,
  then 429 with `Retry-After`. Anyone who knows your email can therefore lock you out of the login form
  for up to 15 minutes by guessing; the CLI is unaffected.
- **Wrong current password on `/api/auth/password` is a 400**, not a 401, so the web app's "any 401
  means the session is gone" handler does not throw you to the login page.
- **Logout works without a session** (204, idempotent), so it is also reachable when auth is required.
- **CSRF:** with auth on, non-GET requests need an `Origin` equal to the request's own origin, or
  `Sec-Fetch-Site` of `same-origin`/`none`; otherwise 403 `csrf_rejected`.
- **Dev proxy:** Vite's `/api` proxy now uses `changeOrigin: false`, because the CSRF check compares
  `Origin` with the `Host` the API receives.

## Rollout (in this order)

Full runbook, rollback and account management: [`deploy/README.md`](../../deploy/README.md#enabling-login-on-an-existing-deployment-replaces-basic-auth).
The order matters. Until step 4, basic auth still guards the site; nothing is deleted until step 6.

1. Merge, and wait for the images workflow (`.github/workflows/images.yml`) to go green.

2. Roll the new images out **while the old manifests are still applied** (`AUTH_REQUIRED` unset means
   off; the migration runs on start):

   ```bash
   kubectl -n flight-log rollout restart deploy/api deploy/web
   ```

   ```bash
   kubectl -n flight-log rollout status deploy/api
   ```

3. Create your user on the seeded default user, so the existing flights stay yours (prompts for the
   password twice, no echo):

   ```bash
   kubectl -n flight-log exec -it deploy/api -- sh -c 'cd apps/api && npm run user:create -- --adopt-default --email you@example.com --name Wyatt'
   ```

4. Apply the new manifests (`AUTH_REQUIRED=true`, no basic auth):

   ```bash
   kubectl apply -k deploy/k8s/apps/flight-log
   ```

   ```bash
   kubectl -n flight-log rollout status deploy/api
   ```

5. Confirm health is public, data needs a session (expect 200 then 401), and that you can sign in
   in the browser:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' https://flights.wyattmunson.com/api/health
   ```

   ```bash
   curl -s -i https://flights.wyattmunson.com/api/flights | head -1
   ```

6. Only then remove the old pieces (`kubectl apply` does not delete dropped objects):

   ```bash
   kubectl -n flight-log delete middleware basic-auth
   ```

   ```bash
   kubectl -n flight-log delete secret flight-log-basic-auth
   ```

Rollback before step 6: check out the previous `deploy/k8s/apps/flight-log` and `kubectl apply -k` it.

## Pitfalls

### The user has to exist before `AUTH_REQUIRED=true` is applied

Symptom: with auth on and no account, every request is 401 and nobody can sign in. There is no signup
page and no reset flow.

Correct approach: run step 3 before step 4. If it happens anyway, the `kubectl exec` command in step
3 still works against the running pod, because the CLI talks to the database directly.

### `user:create --adopt-default` fails with "already has a password"

Correct command when you really do want to replace it:

```bash
kubectl -n flight-log exec -it deploy/api -- sh -c 'cd apps/api && npm run user:create -- --adopt-default --force --email you@example.com'
```

Notes: to change a password without touching the account otherwise, use `user:set-password --email …`.
It also signs that user out everywhere.

### Quoting a multi-word `--name` inside `sh -c '…'`

The whole command sits in single quotes, so `--name "Your Name"` breaks. Use a one-word name, or
change it later. Nothing else about the account depends on the display name.

### Login redirect loop when a session was lost while the app was open (found and fixed in testing)

Symptom: after deleting the session row server-side, clicking a nav link blanked the page and React
logged "Maximum update depth exceeded". TanStack Query keeps the last good `/auth/me` data next to a
later error, and `LoginPage` treated that stale data as "signed in" and sent the user back, where the
route guard sent them to `/login` again.

Fix: `LoginPage` checks `me.status === 'success'`, not `me.data`. A regression test
(`session lost while signed in` in `apps/web/test/auth.test.tsx`) fails without it.

### Logins fail in dev with 403 `csrf_rejected`

Cause: a proxy that rewrites `Host` (Vite's `changeOrigin: true`) makes the browser's `Origin` differ
from the `Host` the API sees. Only matters with `AUTH_REQUIRED=true`.

Fix: `changeOrigin: false` in `apps/web/vite.config.ts`. Any other reverse proxy in front of the API
must pass the original `Host` through (Traefik does by default).

### Testing a production build over plain http

`NODE_ENV=production` makes the cookie `Secure`, which browsers drop over http, so login appears to
succeed and the next request is 401. Set `COOKIE_SECURE=false` for that test only.

## Known gaps

- **Not run against a cluster.** In particular, `kubectl exec … npm run user:create` runs inside a
  pod with a read-only root filesystem (`HOME=/tmp` is writable, so `npm run` should work, but this
  was not tried). If npm complains, the same script can be run as
  `sh -c 'cd apps/api && /app/node_modules/.bin/tsx src/auth/cli.ts create --adopt-default …'`.
- **Single API process.** The login throttle and import previews are in memory. A second replica
  would split the throttle counters.
- **No signup, password reset, email verification, MFA or roles**, by design. The schema leaves room
  for a later `oidc_subject` column; it is not added.
- The `requestLog` line shows the path relative to the router that handled the request (for example
  `POST /login`), which predates this change. It contains no query strings, bodies or cookies.
